# 验收一个 issue

你是验收者，不是实现者。人不参与验收，你的结论就是这个 issue 能不能关闭的依据。像一个挑剔的用户那样，独立判断 issue 的目标是否真的达成，不要复述实现者的说法。

## 前提

- 不能验收自己实现的 issue。看 issue 的认领留言写的是哪个 agent，以及相关 commit 的作者说明。
- 只读：不改业务代码，不推送修复。发现问题就写进结论；超出这个 issue 范围的问题另开 issue。
- 遵守 [AGENTS.md](../AGENTS.md) 的大麦网安全规则：不登录，不下单，遇到风控就停下并写进结论，截图里不能出现账号信息。

## 步骤

1. **准备**：`git fetch && git worktree add --detach ../theFlash-accept-<编号> origin/main`。读 issue 正文（尤其是“验收”和“约束”两节）、实现者的汇报、相关 commit（`git log --grep "#<编号>"`），以及它们引用的 `docs/decisions/` 和 `docs/subsystems/` 文档。
2. **自动检查**：在你的 worktree 里跑 `make check`，必须全部通过；确认实现 commit 上的 CI 是绿的（`gh run list --branch main --workflow test.yml`）。CI 根本没启动（见流水线的 [CI 不可用时](../docs/subsystems/pipeline.md#ci-不可用时)）时，其余各步照做，结论写“除远程 CI 外通过”并保留 `待验收`，CI 恢复、那个 commit 补跑变绿之后再关闭。
3. **逐条验收标准，独立验证**：
   - 按 issue 要求的场景，在真实环境里运行。至少一部分样本要自己重新找，不能只用实现者贴的链接。
   - 用浏览器（computer use）打开同一个真实页面，逐项对照程序的输出。没有浏览器能力时，用 Playwright 打开页面截图对照，并在结论里说明。
   - 每一条标准记下：怎么验的、看到了什么、结论（通过 / 不通过 / 没验）。
4. **试着弄坏它**：边界和异常输入（各种链接格式、不存在、无效输入、断网、场次很多的演出、特殊字符等），看输出是否看得懂、会不会崩溃。
5. **核对实现者的证据**：抽查 commit 正文里说“改动前失败”的测试，把相关修改回退后重跑，确认测试真的变红；对照 [code-standards 的验收标准](../docs/code-standards.md#验收标准)，看有没有遗漏；判断“Not tried”里的内容会不会影响 issue 的目标。
6. **写结论**（评论在 issue 上）：
   - **通过**：列出每条验收标准的验证记录，然后去掉 `待验收` 标签并关闭 issue：`gh issue edit <编号> --remove-label 待验收 && gh issue close <编号> --reason completed`。
   - **不通过**：列出每个问题：复现步骤、期望结果、实际结果、证据（命令和输出，或截图）。把标签从 `待验收` 换成 `验收未通过`，issue 保持打开。
   - 范围外的新问题：各开一个新 issue，在结论里附上链接。
7. **收尾**：结论写完就删掉自己的 worktree 和这次验收建的其他目录，命令见 [AGENTS.md 会话流程第 10 步](../AGENTS.md#一次会话的流程)。

## 规则

- 结论只基于你自己跑出来的证据。
- 没验的标准写“没验”和原因，不能省略。
- 有任何一条标准不通过，结论就是不通过。
