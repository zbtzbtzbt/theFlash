# Issue 优先级

> 每个 issue 是 P0～P3 的哪一档，agent 按什么顺序挑

## 职责和边界

回答两个问题：这个 issue 有多重要、多紧急；现在所有能开工的 issue 里，下一个该做哪个。为什么这样分见 [0016](../decisions/0016-issue-priority.md)。

它**不**做的事：

- 不调用大模型，不替 agent 判断一个 issue 重不重要。定级是 agent 按下面的标准做的判断，命令只负责把判断记下来、把顺序算出来。
- 不安排谁做什么。队列对所有 agent 都一样，挑哪个、改哪些模块还是由认领的 agent 决定，冲突由[认领租约](claim-lease.md)拦。
- 不改 issue 的正文、标题、assignee；只碰 `P0`～`P3` 四个标签。`等裁决` 标签由提出裁决的 agent 或 owner 手动加减。

## 两个轴

**重要**：不做，项目会在下面某一处出错。

1. 安全规则和 owner 的决定：不下单、凭据不进仓库、测试不碰真实大麦、遇到风控就停（[Owner 的决定](../code-standards.md#owner-的决定)）。
2. 当前阶段的目标（见下面的“当前阶段”）。
3. 用户核心路径的正确性：查询 → 盯票 → 提醒 → 辅助抢票（#6 裁决的范围）给出错的结果，或者静默失效。
4. 守护本身失效：以某个保证命名的测试或检查守不住它（假绿）。后面每个改动都靠这些测试判断对错，所以守护的洞和功能的洞一样重要。

只影响提示文字、单个罕见环境、开发便利、个人偏好的重构，算不重要。

**紧急**：不现在处理，代价会随时间涨。

1. main 的 Test 红，或者发版、合并被挡。
2. 安全规则此刻正在被违反：凭据已经进了仓库或日志、某条路径会访问真实大麦或提交订单。
3. 用户正在用的功能此刻坏了，例如大麦改版让查询或盯票失效。
4. 正在挡住别的 agent：同一个原因让进行中的 PR 反复被打回、`make check` 在某种常见环境下直接失败。
5. 有外部时间点：开售时间、owner 给的截止时间，按正常排队赶不上。

“已经有人在做”“已经合入在等验收”说明它不紧急，不说明它不重要。

## 四个档

| | 紧急 | 不紧急 |
| --- | --- | --- |
| **重要** | **P0**：现在就做，排在所有新工作前面 | **P1**：主线，当前阶段的工作在这里 |
| **不重要** | **P2**：P0、P1 都没有可做的时候再做，限时 | **P3**：不主动做，队列里没有别的才做 |

P1 排在 P2 前面：重要不紧急的事没有截止时间，最容易被一件件“急事”挤掉，而架构、守护、流水线恰好都在这一格。

P0 应该很少。同时有三个以上的 P0，多半是定级失准（#69 把这一条加进夜间复盘）。main 红本身就是 P0，修它不用先开 issue；修不了才开 issue，定成 P0。

## 当前阶段

owner 定的（[Owner 的决定](../code-standards.md#owner-的决定)，2026-10-14）：先把架构搭对，在正确的架构上迭代。落到定级上：

- 模块边界和接口（访问大麦的统一出口、界面的进程模型）、单一事实来源、守护和测试的可信度、agent 协作流水线（认领、优先级、审查、合并、验收、复盘、调度），都算“重要”。
- 回答“现在的架构对不对”的调查也算重要，例如 #8 统计电脑版不卖的演出：答案可能推翻数据源的决定（[0001](../decisions/0001-damai-event-data-source.md)）。
- 新功能如果要建在还没落地的架构上，先把缺的那块架构拆成单独的 issue，再在功能 issue 的正文里写 `依赖：#<架构 issue>`。功能 issue 照常按重要和紧急定级，依赖没关之前它不进队列。

阶段变了（例如架构稳定下来，开始以功能为主），由 owner 改 code-standards 里那一条，这一节跟着改。

## 同一档里先做哪个

1. **依赖**：issue 正文里一行 `依赖：#4、#26`（也认 `前置：`、`Depends on:`、`Blocked by:`，半角全角冒号都行，前面可以有列表符号）。列出的 issue 还开着，这个 issue 就不进队列。引用行（`>`）和代码块里的不算，和租约的格式一样只认正文自己说的话。依赖关了（不管是做完还是不做了），它自动回到队列。
2. **挡路的不低于被挡的**：一个 issue 挡着一个比它高的 issue，它就该提到那一档。队列会在它下面写一行提醒，由看到的 agent 用 `triage` 改级。命令不自动改，因为改级要留下理由。
3. **同一档里号小的在前**。这只是给读的人一个稳定的顺序：同一档的 issue 一样重要，认领同一档里的任何一个都不拦，按模块冲突和自己能做什么挑。

## 等 owner 的 issue

花钱、真实账号、法律风险、用户可见的产品取舍要 owner 裁决（[AGENTS.md](../../AGENTS.md)）。这类 issue 加 `等裁决`：

- 不进队列，`claim` 拒绝认领，`--out-of-order` 也绕不过去：那是 owner 的决定，不是顺序问题。
- 照样定级。owner 看 `gh issue list --label 等裁决`，按优先级先裁 P0。
- 裁决之后由 owner 或转述裁决的 agent 去掉 `等裁决`，在 issue 上写明裁决内容。

## 谁定级、怎么改

- 开 issue 的 agent 同时定级：正文末尾写一节“优先级”，两个轴各一句理由，再加标签；或者开完就跑一次 `triage`。
- 看到没定级的 issue，先定级再挑工作：队列把它们排在最前面就是为了这个。
- 改级用 `scripts/claims triage`：先发一条 `## 优先级` 评论（谁、哪一档、原来是哪一档、两个轴各自的理由），再重读确认没有和另一条并发定级撞上（同一轮里更早的 `## 优先级` 评论算数），随后换掉标签（包含已有标签的实际大小写拼写）并再读回核对（`gh issue edit` 底层的加减标签是两个独立请求，若第一次部分生效会自动补齐一次），保证成功返回时 issue 上只有一个优先级标签，且每次变化都有理由。不要手改标签。
- owner 在 issue 上说过的优先级，agent 不改；觉得不对就在 issue 上写理由，等 owner。

## 事实来源

| 事实 | 来自 |
| --- | --- |
| 一个 issue 的优先级 | 它的 `P0`～`P3` 标签。一个都没有是“没定”；有两个以上看不出哪个算数，也当没定，要用 `triage` 定成一个 |
| 为什么是这一档 | issue 上最新一条 `## 优先级` 评论，或者开 issue 时正文里的“优先级”一节。只给人读，命令不解析 |
| 依赖 | issue 正文里的 `依赖：#N` 行（[`priority::depends_on`](../../backend/src/claim/priority.rs)） |
| 有没有人在做 | [认领租约](claim-lease.md)的看板：租约还算数就不在队列里；已过期的留在队列里并提示先收回 |
| 做完了、在等验收 | `待验收` 标签 |
| 验收没通过 | `验收未通过` 标签：回到队列，提示是返工 |
| 只能由谁做 | `指派:<agent>` 标签 |
| 要等 owner | `等裁决` 标签 |

数据一次取齐：`repos/<仓库>/issues?state=open` 拿所有打开的 issue 的标签和正文（不取评论，一百个 issue 一个请求），再加上租约看板本来就要取的那些。

## 运行路径

```sh
scripts/claims queue                         # 现在能开工的，按优先级排，以及其他 issue 为什么不在里面
scripts/claims queue --agent Codex           # 按 Codex 能认领的算：指派给别人的不算
scripts/claims queue --json                  # 同上，给调度程序读：next、ready、waiting
scripts/claims triage --issue 49 --agent Claude --priority P2 \
    --important "产品代码不受影响，只是测试拿程序路径的写法错了" \
    --urgent "worktree 名字带中文时 make check 直接失败，挡住正在干活的 agent"
scripts/claims claim --issue 49 --agent Claude --modules frontend/src \
    --out-of-order "前面的 P1 都要访问真实大麦，我在云端"
```

`queue` 的输出分三段：可以开工的（没定级的在最前面，然后 P0 到 P3），不在队列里的（认领中、认领读不出来、待验收、等裁决、被依赖挡着、指派给别人，各列出号和优先级），最后一行是“下一个”和认领它的命令。`--replay`、`--now`、`--repo`、`--dry-run` 和其他子命令一样（[认领租约](claim-lease.md#运行路径)）。

## 认领时什么时候拒绝

`claim` 先做租约的检查（别人在做、模块重叠……，见[认领租约](claim-lease.md#什么时候拒绝)），通过之后再按 [`priority::decide`](../../backend/src/claim/priority.rs) 看顺序。租约的拒绝更具体，所以先说。

| 情况 | 怎么继续 | `--out-of-order` 能放行吗 |
| --- | --- | --- |
| 不是打开的 issue | 换一个 | 不能 |
| 带 `等裁决` | 先做不受它影响的部分 | 不能 |
| 带 `待验收` | 按 [prompts/acceptance.md](../../prompts/acceptance.md) 独立验收，不要重复实现 | 不能 |
| 没定级，或者有两个优先级标签 | 先 `triage` | 不能：不知道它的级别，就谈不上顺序 |
| 正文依赖的 issue 还开着 | 先做依赖 | 能，例如依赖的代码已经合进 main、只差验收 |
| 队列里有更高一档、这个 agent 现在就能认领的 issue | 先做它们 | 能，例如前面的都要访问真实大麦而你在云端 |

放行时，跳过了什么和理由写进认领评论的 `- 不按顺序:` 一行，下一个读 issue 的 agent 和夜间复盘都看得到。比较只看这个 agent 能认领的 issue：指派给别人的、正在被做的、等验收的、等裁决的、被依赖挡着的都不算“排在前面”。

## 和别的子系统的关系

- [认领租约](claim-lease.md)：队列用它的看板判断谁在做；认领评论多了一个可选字段 `不按顺序`，租约的解析不读它。
- [调度程序](dispatch.md)（#14）直接复用 `claim::priority`、`claim::read_lease` 和分支推送读取函数，按与 `queue` 相同的规则决定派什么新活并跳过 `等裁决`。
- 合并之后审查者要给 issue 加 `待验收`（[AGENTS.md](../../AGENTS.md#审查和合并)）。漏加的话，已经做完的 issue 会以原来的优先级出现在队列里，像是没人做过；看到这种情况，先查 `git log origin/main` 有没有提到它的 commit。

## 失败行为

- 取不到打开的 issue 列表：退出码 2，打印“问 GitHub 要 … 失败”，什么都不改。`claim` 也一样：判断不了顺序，就不认领。
- `triage` 发出评论之后发现同一轮已有更早的 `## 优先级` 评论：退出码 1，不改标签，以更早那条为准。
- `triage` 发出评论之后改标签失败，或补齐后读回仍不是单一的目标优先级：退出码 2，打印补标签的 `gh issue edit` 命令。评论是记录，标签补上就行；再跑一次 `triage` 会多发一条评论。
- `triage` 的目标已经是那一档：什么都不发，退出码 0。
- 一个 issue 标着 `认领中`，看板却没读到它（两次请求之间有人刚认领）：当成认领中，不放进队列。
