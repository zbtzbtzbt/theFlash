## 维护参考文档

改动影响了文档里写过的职责、接口、状态转换、运行路径、兼容规则或失败行为时，在同一个改动里更新对应的参考文档。不改变这些契约的内部重构，不需要改文档。

每个事实只写在一份参考里，其他地方链接过去。链接到源码文件和具名符号，不要复制容易变的实现细节。写清楚签名本身表达不了的字段含义和约束。

新建一份参考时，一级标题下面先写一行 `> 一句话`（上面的索引用它当第一列），再写清楚：职责和边界、事实来源（source of truth）、主要运行路径、状态转换、重要约束、已有的验证命令，以及相关的失败和兼容行为。当前行为和提议的变化分开写，提议放在 issue 或 PR 里。

文档里写到的安全或数据问题，就是一个打开的 bug，不是描述。写下这样一句话时，在同一个 commit 里开一个 issue。

## 描述一个改动的语义变化

对每个受影响的子系统，写出可观察的变化：触发条件，改动前后的行为。相关时写出接口、状态、兼容性和失败行为的变化。链接受影响的参考文档、实现和验证证据。重构保持原有行为时，明确说出来。

## 审查一个改动

1. 找出受影响的子系统和实际运行的路径。
2. 对照 base 和 head 的实现，核对声称的前后行为。追踪改动行之外的调用方和状态转换。
3. 确认改变的契约出现在对应的参考文档里，源码链接仍然有效。
4. 确认引用的测试或运行证据确实覆盖了声称的行为。列出没有跑的检查。

只改文档不能证明实现是对的。行为变化仍然需要测试和运行证据。
