# 0017. 协作流水线：标签是状态，各站写在一处，先收尾再开始

- 状态：采用
- 日期：2026-10-14
- 相关：#69、#68（优先级）、#15（合并闸门）、#16（认领租约）、#14（调度程序）、#81、#63、#102、#103

## 背景

theFlash 照着 magpie 搭了大部分零件（[magpie-study.md](../magpie-study.md)）：AGENTS.md 当路由表、LESSONS.md 当错题本、code-standards 的验收标准、合并时核对 head 的闸门、带过期时间的认领、独立验收、夜间复盘。2026-10-14 一晚上五六条线并行跑下来，零件各自能用，零件之间的交接处在漏：

- 一件活的完整路径散在五份文档里（AGENTS.md、work-tick、acceptance、merge-gate、claim-lease），没有一份说清 issue 有哪些状态、每次标签变化由谁负责。
- 交接靠手动加标签，最常漏的是合并之后的 `待验收`。10-14 上午第一次在真实仓库上跑 `scripts/claims queue`（#68），7 个已经合入的 issue 没有这个标签，以原来的优先级留在队列里，像是没人做过。
- 审查这一站被跳过：闸门进 main 之后的 7 次合并里，6 次没走闸门（#81）。
- work-tick 第 5 步只写“挑一个最影响用户的 issue”；`要修改` 的 PR 由谁、在第几步处理，work-tick 里没有。
- 三个会话十分钟里各开一个 issue 报同一件事（#63、#65、#67）：开 issue 前不搜重复，issue 也没有固定写法。
- GitHub Actions 因账单起不来（#63）时，job 显示 failure，按 work-tick 第 1 步会被当成 main 红去改代码；流程里没有“CI 不可用”这种状态。
- 夜间复盘只看 commit 写得好不好，不看活卡在哪一站。

约束：和 [0008](0008-claim-lease.md)、[0016](0016-issue-priority.md) 一样，状态只能放在 GitHub 上，所有 agent 共用一个账号，不能依赖常驻服务；GitHub Actions 本身可能不可用。

## 考虑过的选项

- **保持现状，规则继续分散在各份文档里**：不用改，但每个 agent 都要读完五份文档自己拼出流程，拼法不一样，交接处就漏。
- **用 GitHub Actions 按标签事件自动推进状态**（例如合并后自动加 `待验收`）：机械、及时，但 Actions 恰恰在这时候不可用（#63），而且又多一套要审查的工作流和权限。适合放进已有的命令行工具（合并闸门、调度程序），不适合单独做一套。
- **GitHub Projects 看板**：状态可视，但要额外的 API 和权限，issue 页面上看不到，0008 不选它的理由同样适用。
- **一份流水线参考 + 标签就是状态 + 一个拉取顺序**（选中）：不增加任何运行的东西，每个 agent 读一份文档就知道活在哪、下一步谁做；能机械化的交接，以后放进合并闸门和调度程序里。

**顺序怎么排**：考虑过“先开新活、空了再收尾”（产出看起来多，但审查和验收要换厂商，最容易积压，积压的 PR 越久越难合）和“完全按优先级，不管站”（一个 P1 的新 issue 会排在一个等了半天的 P1 审查前面）。选了“先收尾，再开始”：main 红和 P0 打断一切，其余按站从后往前——发版、自己的返工、审查、验收、定级、开新活。这和调度程序已有的派活顺序（[dispatch](../subsystems/dispatch.md#什么事件派给谁)）是同一个原则。

## 决定

- [docs/subsystems/pipeline.md](../subsystems/pipeline.md) 是流水线的唯一一份地图：各站、issue 和 PR 的标签状态机、每次转换谁负责、每一站进站和出站要什么、这一轮先做什么、在制品限制、issue 的写法、owner 在哪里、CI 不可用时怎么办、复盘看哪些流动指标。站内细节仍在各站自己的文档里，地图只链接过去。
- AGENTS.md 只做路由：会话流程开头指向“这一轮先做什么”，认领指向 `queue`，开 issue 指向“issue 怎么写”。work-tick 按新顺序重排，把“自己的返工”单列一步。
- 在制品限制写成规则：一个会话一个认领；自己有返工时不开新活；一个 issue 一个 PR。现在没有机器强制，夜间复盘看。
- CI 不可用是一种状态：不改代码、确认有 P0 + `等裁决` 的 issue、照常实现审查验收、不合并不发版、恢复后补跑。
- 夜间复盘加一节“流水线健康和优先级校准”。
- 两处交接现在靠手动、应该机械化，各开一个 issue，不在这次改动里做：合并闸门合入后自动给 issue 加 `待验收`（#102）；调度程序派新活时按优先级队列挑、不派 `等裁决` 的 issue（#103）。

## 后果

- 变容易：一个新会话读 AGENTS.md 和 pipeline.md 就知道活在哪一站、自己下一步做什么。夜间复盘有了看“流动”的清单，卡住的站会变成 LESSONS 里的证据。owner 的待办只有一个查询（`等裁决`）。
- 变难：多一份要和各站文档保持一致的文档。规则是“站内细节以各站文档为准，不一致时改地图”，所以各站改了交接方式，要在同一个改动里改 pipeline.md。
- 在制品限制和“先收尾再开始”目前靠 agent 读文档遵守；`claims claim` 不知道你手里还有没有别的活（同厂商的会话分不出来，见 0008）。如果复盘反复看到同一个会话手里压着返工还在开新活，就在调度程序里加限制，而不是在认领里猜会话身份。
- 什么时候重新考虑：合并闸门在服务端被强制（#81 的裁决）或者调度程序接管了全部派活之后，这份文档里“谁让它出去”的大部分会变成“工具自动做”，到时候把手动步骤删掉，只留状态和条件。
