# 0016. issue 按重要和紧急分成 P0～P3，认领按优先级排队

- 状态：采用
- 日期：2026-10-14
- 相关：#68、#69、#16（认领租约）、#14（调度程序）

## 背景

2026-10-14 上午，仓库里有 30 多个 open issue，没有一个有优先级。`prompts/work-tick.md` 只写了“挑一个没人认领、最影响用户的 issue”，每个 agent 对“最影响用户”的理解不同，结果是顺手的、最近看到的先做，没有截止时间的地基性工作（#8 回答数据源选得对不对、#26 界面的进程模型）一直没人碰。owner 的判断是 theFlash 现在应该先把架构搭对，再在上面迭代；这个判断在挑 issue 的那一刻没有任何东西把它带进来。

同一个上午还看到两件事：

- 三个会话在十分钟里各开了一个 issue 报同一件事（#63、#65、#67，GitHub Actions 因账单停了）。重要又紧急的事没有一个统一的地方显示出来，大家只能各自报。
- 几分钟里又冒出 12 个新 issue（#70～#81）。没有定级这一步，它们和老 issue 混在一起，谁先谁后全凭读的人。

约束：

- 和[认领租约](0008-claim-lease.md)一样，状态只能放在 GitHub 上，所有 agent 共用一个账号，没有 Projects 字段可用。
- 判断要机械：调度程序（#14）和 agent 对“下一个是谁”要得到同一个答案。
- owner 要求用“重要 / 紧急”两个轴的四象限分成 P0～P3。

## 考虑过的选项

**怎么分档**

- **四象限映射到 P0～P3**（选中）：P0 重要且紧急，P1 重要不紧急，P2 紧急不重要，P3 都不。两个轴各自好判断，四个档直接由两个是非题得出，定级的理由天然就是两句话。
- **只按严重程度分（致命 / 严重 / 一般 / 轻微）**：bug 好分，但架构、调查、流程类的 issue 没有“严重程度”，而它们恰好是当前阶段最该做的。
- **打分排序（RICE、WSJF 之类）**：更细，但每个 issue 要估四五个数，agent 之间估出来的数没法比，排序会被估值噪声主导。
- **不分档，只排一个全局顺序**：最直接，但每加一个 issue 都要重排，并行的 agent 会同时改顺序。

**P1 和 P2 谁在前**：经典四象限把“紧急不重要”交给别人做，排在“重要不紧急”后面。这里也这样排：重要不紧急的事没有截止时间，最容易被一件件急事挤掉，而当前阶段的架构工作全在这一格。紧急但不重要的事（某个环境下测试路径写错）往往小而具体，等 P0、P1 都没有可做的时候清掉。

**存在哪里**

- **标签**（选中）：`gh issue list --label P0` 就能过滤，GitHub 页面上一眼可见，一次请求就能拿到所有 open issue 的标签。改级的理由写在一条 `## 优先级` 评论里。
- **正文里的一行“优先级：P1”**：改级要改别人的正文，历史看不到，而且要取每个 issue 的正文再解析。
- **Projects 自定义字段**：要额外的 API 和权限，issue 页面上看不到（和 0008 不选它的理由一样）。

**认领时要不要强制**

- **只在 `queue` 里排好，认领不管**：最省事，但“按优先级来”又回到了 agent 自觉。
- **认领低优先级的直接拒绝，没有例外**：会卡死合理的情况——前面的 issue 要访问真实大麦而 agent 在云端（#9 的裁决），或者依赖的代码已经合进 main、只差验收。
- **拒绝，但允许写明理由后放行**（选中）：和认领租约的 `--overlap` 同一个模式。正确的做法最省事，偏离要留下理由，理由写进认领评论，夜间复盘看得到。

**依赖怎么表达**

- **正文里一行 `依赖：#N`**（选中）：列表请求本来就带正文，不用多发请求；开 issue 的人写，别人也能补。
- **GitHub 的 sub-issue / tracked-by**：要另一套 API，嵌套关系和“必须先关”不是一回事。
- **评论里声明**：要取每个 issue 的全部评论，三十多个 issue 就是三十多个请求。

## 决定

- 四个标签 `P0`～`P3`，含义和判断标准写在[Issue 优先级](../subsystems/issue-priority.md)里；外加一个 `等裁决` 标签，等 owner 的 issue 不进队列、不能认领。
- [`backend/src/claim/priority.rs`](../../backend/src/claim/priority.rs) 算队列：打开的 issue 里去掉认领中、待验收、等裁决、被依赖挡着、指派给别人的，剩下的按“没定级、P0、P1、P2、P3，同一档号小的在前”排。
- 三个命令放在 [`scripts/claims`](../../scripts/claims) 里，而不是另起一个：认领和挑 issue 是同一件事的两半，看板（谁在做）也是队列的输入。
  - `queue`：给人读的列表和给调度程序读的 JSON。
  - `triage`：先发 `## 优先级` 评论，再在一次编辑里换标签，issue 上永远只有一个优先级标签。
  - `claim`：租约的检查之后再看顺序。没定级、等裁决不能认领；依赖没关、有更高一档的可做，要 `--out-of-order <为什么>`。
- 当前阶段（先搭架构）记进 [code-standards 的 Owner 的决定](../code-standards.md#owner-的决定)，它决定了什么算“重要”。
- 新功能要建在还没落地的架构上时，把架构拆成单独的 issue，功能 issue 写 `依赖：`。这样“在正确的架构上迭代”是队列算出来的结果，而不是一句提醒。

## 后果

- 变容易：`scripts/claims queue` 一条命令回答“下一个做什么”；调度程序读 `--json` 的 `next`。owner 用 `gh issue list --label 等裁决` 看自己欠着哪些裁决，按优先级先裁 P0。没定级的新 issue 排在最前面，下一个看到的 agent 先定级。
- 变难：开 issue 多一步定级；认领多一道检查，跳过队列要写理由。定级是判断，两个 agent 可能定得不一样——所以改级必须留理由，夜间复盘看定级有没有失准（#69）。
- 合并之后漏加 `待验收` 的 issue 会以原来的优先级留在队列里，看起来像没人做过（2026-10-14 第一次在真实仓库上跑 `queue` 就看到了 7 个）。这是合并那一步的漏洞，不是队列的；在合并闸门里自动加标签之前，看到它的 agent 先查 `git log origin/main`。
- 同一档里不强制顺序：号小的在前只是为了列表稳定。如果以后同一档里积压很多、需要更细的顺序，再考虑在档内加一个依据（例如阻塞了几个 issue），而不是加更多的档。
- 什么时候重新考虑：P0 长期超过三个、或者大部分 issue 都挤在 P1，说明两个轴的标准太宽，要收紧“重要”的定义；当前阶段结束（owner 改了那条决定）时，重新审一遍所有 P1。
