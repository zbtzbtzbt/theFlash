# 0010. 有事才启动一个全新 agent 会话的常驻调度程序，混合部署

- 状态：采用
- 日期：2026-10-14
- 相关：#14、#9（owner 裁决：混合）、#16（认领租约）、#15（合并闸门）、#17（launchd 验证任务）

## 背景

项目的前提是“不等人”，但到 2026-10-14 为止，每一轮工作都靠 owner 手动开一个会话：

- 工作循环跑在 owner Cursor 的一个聊天会话里，每 30 分钟醒一次。关掉窗口就停，空闲时也在消耗，同一个会话的上下文越来越长（#14）。
- 夜间复盘的 Cursor Automation 要 owner 手动保存才生效，一次都没跑过；LESSONS.md 的水位线一直是 `none`（#9）。
- 另一个厂商的 agent（Codex、CodeBuddy）只有在 owner 把 prompt 粘过去时才工作，验收和修复都要人转发。
- 这一夜用临时脚本（`~/Desktop/theFlash-night/bin/dispatcher`、`run-task`、`wait-net`）跑了 6 条线，证明“机械派发 + 一个任务一个全新会话”是可行的：标签决定角色、厂商错开、断网等待、失败重试。但它们是一次性的 bash，没有测试、没有上限、没有文档，也不知道谁在做哪个 issue。

owner 对 #9 的裁决是**混合**：不访问大麦的任务（夜间复盘、修 CI、审 PR）在云端跑；访问大麦或要浏览器验证的任务（实现、验收、改版巡检）在 owner 的 Mac 上跑。这条已经写进 [code-standards 的 owner 决定](../code-standards.md#owner-的决定)。

约束：

- 调度程序本身不能调用大模型——它每分钟醒一次，调模型既花钱又会让“派不派活”变得不可复现。
- 所有 agent 共用一个 GitHub 账号，`user.login` 分不出是哪个 agent（#15），所以“谁在做这个 issue”只能看评论自己声明的字段。
- agent 的命令行和凭据是本机的东西，不能进仓库。Homebrew 装的 codex 0.152 用 ChatGPT 账号登录时不支持配置里的模型，要用 ChatGPT.app 自带的那个二进制，所以路径必须可配。
- 会话会花钱，而且今晚已经有多条线在跑：必须有并发上限、每日上限，以及“只认某个标签”的开关，否则装上就会去抢别人手里的 issue。

## 考虑过的选项

### A. 继续用聊天窗口里的定时循环
不用写代码，但窗口一关就停、上下文越来越长、同一个会话什么都做。#14 就是为了取代它。

### B. GitHub Actions 上的定时工作流派发
不占 owner 的机器，但云端跑不了要访问大麦和浏览器的验收（#9 的裁决正是因此选了混合），而且 agent 的凭据要进 GitHub secrets。不解决本机那一半。

### C. 临时 bash 脚本留下来（今晚那套）
已经跑通，但判断逻辑散在 `gh ... --jq` 和标签字符串里，没法写测试；要加上限、认领、超时释放，脚本会长成另一个没人敢改的东西。

### D. 常驻程序 + 纯函数判断（选它）
一个 Rust 子命令 `scripts/dispatch`：`gh api` 读 GitHub → 纯函数算出“该启动哪些会话、哪些不启动、为什么” → 启动 agent 命令行。判断不碰网络、不碰进程，所以可以用保存下来的真实 GitHub 响应回放测试；启动、收尾、服务登记各是一层薄壳。常驻靠 launchd（macOS）和 systemd user unit（Linux），因为要在合盖、重启和终端关掉之后仍然活着。

为什么是 Rust 而不是 Python：`scripts/claims`（#16）和 `scripts/merge-gate`（#15）已经是这个形状——`gh api` 取数据、纯函数判断、回放测试，三者共用一套“谁是哪个 agent”的名字规则和一套退出码；调度程序是它们的调用方，放在一起改比放在另一门语言里改更安全。#17 的 `scripts/validation.py` 管的是“一个长时间运行的验证任务”，和这里不重叠。

## 决定

1. **一个任务一个全新会话，调度程序自己不调模型。** 每 60 秒看一次 GitHub：`待审查` 的 PR、`要修改` 的 PR、`待验收` 的 issue、`验收未通过` 的 issue、没人认领的 issue、main 上 Test 红了、到点的定时任务。每件事算出一个稳定的任务编号（`accept-22-a1`、`review-33-a1`），编号派过就不再派。
2. **角色决定厂商。** 审查和验收必须交给实现者以外的厂商；`要修改` 和 `验收未通过` 回到实现者自己的厂商；其余交给今天派得最少的那个厂商，同样忙时按设置里的顺序。实现者是谁，先看认领租约的 `## 认领` / `## 心跳` 评论（#16），没有就看 issue 上**最早**的 `Agent:` 签名——最后说话的人往往是验收者（#22 上 CodeBuddy 实现、Codex 验收）。
3. **上限写在设置里，超出就排队并在 issue 上说明一次。** 并发上限、每日会话上限、会话超时时间、只认某个标签、忽略哪些 issue。新装的设置是 `max_sessions: 1`、`max_sessions_per_day: 2`、`require_label: 演示:调度`，所以第一次装上不会碰任何人手里的活。
4. **#9 的本机路由边界：哪些活归云端，本机就不派。** 设置里的 `cloud_roles` 默认是 `review`、`fix-ci`、`nightly-review`；本机看到这些角色时跳过，并在 `plan` 里说明“按 #9 的裁决归云端”。这个字段不创建、保存或验证云端 Automation；云端任务仍需单独部署。要访问大麦或要浏览器验证的 `implement`、`accept` 留在 owner 的 Mac 上。定时任务按设置里的 `HH:MM`（北京时间）每天一次，示例只包含 03:00 夜间复盘，不包含改版巡检。
5. **失败和超时的会话由调度程序收尾。** 非 0 退出或跑过 `session_timeout_minutes`（默认 120 分钟）都调 `scripts/claims reclaim` 释放认领并评论 issue；超时还会停掉整个进程组。`claims` 拒绝收回时，原样把它的话写进评论。协议命令或评论调用失败时下一轮重试收尾。失败或超时的任务只自动再试一次，然后不再动它。
6. **main 红不红只看 Test 工作流。** 被拒绝的 Release run 也挂在 main 的提交上（发布闸门按设计拒绝，#5），把它当成红会派人去修一个正常工作的检查。被取消或没取到 runner 的 run 不算红（今晚 macos-latest 反复如此），只有 `failure` 和 `timed_out` 算。
7. **凭据不进仓库。** 设置文件在仓库外（默认 `~/.config/theflash/dispatch.json`），里面只有命令行和路径；agent 自己的登录由它自己的命令行管。

## 后果

- 变容易：安装并启用服务后，符合设置的 GitHub 事件可以启动全新会话；审查和验收的计划会避开实现者厂商；失败或超时的会话不再悄悄占着认领。派不派活是纯函数，可以用真实响应回放，所以改规则时能先看它会怎么决定（`scripts/dispatch plan` 什么都不启动）。
- 变难：多了一个必须自己看住的常驻程序。它启动的会话会花钱，所以上限和 `require_label` 是默认开着的；要放开，得有人改设置。标签仍然可以被手写绕过（和认领租约一样，#8），这里接受这一点。
- 当前证据边界：macOS 做过安装、单个实现会话和卸载；没有真实演示跨厂商验收闭环，Linux systemd 没有真机安装，云端 Automation 也没有由这个改动创建或启用。因此当前不能说它已经取代聊天循环或完整落地 #9。
- 以后出现什么证据时重新考虑：
  - 如果云端 agent 能做浏览器验证和真实大麦验证，#9 的混合就没必要了，这条和 `cloud_roles` 一起重写。
  - 如果 GitHub 的轮询被限流（每分钟 4 次 `gh api`），改成 webhook 或者拉长间隔。
  - 如果“一个任务一个全新会话”在实践中让 agent 重复读同样的文档、代价太高，再考虑让一个会话连做同一个 issue 的两轮。
