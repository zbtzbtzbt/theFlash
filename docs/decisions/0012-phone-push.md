# 0012. 盯票提醒通过可替换渠道推送，先支持 ntfy

- 状态：采用
- 日期：2026-10-14
- 相关：#11、#20、[0002](0002-watch-timing-and-polling.md)

## 背景

owner 在 #11/#20 裁决先支持 ntfy，同时保留替换渠道的边界。桌面提醒已经有状态去重和开售两阶段内容，手机应接收相同内容；推送不能拖住大麦查询和开售确认。topic 本身也视为凭据。

## 考虑过的选项

1. 在盯票状态循环直接调用 ntfy：改动少，但耦合协议，网络延迟会影响确认时间。
2. 在提醒出口同步等待可替换渠道：保留通知语义，但即使设超时，开售确认也会延迟。
3. 在提醒出口向有界队列投递，由独立异步任务调用渠道：既复用已有去重和正文，也隔离第三方延迟。代价是退出时可能有尚未投递的提醒。

## 决定

采用方案 3。`PushChannel` 只接收标题和正文，ntfy 负责协议和认证；状态去重继续由 `watch::run` 负责。后台任务每条只尝试一次，禁止 HTTP 自动重试和重定向，失败只输出固定打码提示。不重试避免服务端已收下但响应丢失时重复刷屏，不能保证网络故障下手机一定收到。

配置用用户配置目录的 JSON 文件，要求普通文件、严格 0600，拒绝符号链接。JSON 比新引入 TOML 或钥匙串依赖简单，沿用已有 serde_json。topic 和 token 不接受命令行参数，不输出配置、底层错误或服务端响应。服务器只允许 HTTPS 根地址，本机 HTTP 留给离线测试；公共服务器默认 `https://ntfy.sh/`。

ntfy 使用根地址的 JSON 发布接口，正文承载 topic、中文标题和正文，避免中文 HTTP 标题头兼容问题。复用 reqwest/tokio，无新依赖版本；已有 tokio 启用 sync 功能。

## 后果

- 未配置时不开网络客户端、无新增输出，原来的终端和系统提醒保留。
- 队列最多 32 条，每次请求最多 3 秒。满队列丢弃该次手机提醒并说明，盯票照常。正常结束最多等 3 秒；Ctrl-C 立即取消后台任务，未完成的提醒不保证送达。
- 公共 ntfy 是第三方，收到演出、场次、票档、状态和时间；持有公共 topic 的人可订阅。文档要求随机 topic，可选 token 由 ntfy 服务端权限决定。
- 将来增加渠道只实现投递接口和配置变体，不重写盯票时序。需要可靠重试或退出持久化时，应重新评估消息 ID、去重与磁盘凭据边界，而不是直接循环重发。
- 协议依据：[ntfy JSON 发布](https://docs.ntfy.sh/publish/#publish-as-json)、[订阅轮询](https://docs.ntfy.sh/subscribe/api/#poll-for-messages)。
