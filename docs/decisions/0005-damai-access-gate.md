# 0005. 所有大麦请求走同一层：进程内频率上限，跨进程熔断放在用户状态目录

- 状态：采用
- 日期：2026-10-14
- 相关：#4，[0001](0001-damai-event-data-source.md)，[0002](0002-watch-timing-and-polling.md)，[0004](0004-local-event-ui.md)，[0009](0009-launchd-validation.md)

## 背景

#4 要求：所有访问大麦的请求共用一个频率上限；任何一个 theFlash 进程触发风控，其他进程也立刻停止请求，直到 owner 处理。

改动前的事实：

- 风控判断在 `Client::get` 里，只影响当前这一次查询（0001）。
- `theflash watch` 会连续轮询几小时（0002）。
- #3 的本地界面把风控状态记在 Node 进程内存的 `riskStopped` 里，重启服务就没了，也不和 CLI 共享（0004 自己写明这是本轮的代价，由 #4 跟进）。
- 频率上限只有一处：票档请求之间 `sleep(300ms)`，以及读大麦时钟之间 `sleep(250ms)`。两者都不知道同一进程里别的调用方发了多少请求。
- 用户同时开着界面和 `watch` 时，大麦看到的是两边相加的流量；一边触发风控，另一边不知道，会继续请求。这违反 owner 的规则“出现风控提示就停下来，由 owner 决定下一步”（code-standards）。
- 大麦的搜索接口第一次匿名请求就返回滑块验证（0001），所以对请求节奏必须保守。

## 考虑过的选项

**熔断状态放哪里**

1. **用户状态目录下的一个 JSON 文件**（macOS `~/Library/Application Support/theFlash/`，Linux `$XDG_STATE_HOME` 或 `~/.local/state/theflash/`）：任何进程都能读写，重启后还在，不需要常驻服务，不需要新依赖。
2. 一个常驻的本机守护进程持有状态：能做跨进程的令牌桶，但多了一个要启动、要监控、要升级的东西，而且它自己挂掉时所有查询都没法判断状态。
3. 只放内存，各进程自己管：就是改动前的样子，#4 要解决的正是它。

**跨进程是否也共用频率上限**

1. **只在进程内共用频率上限，跨进程靠熔断兜底**：不需要在每个请求的热路径上做文件加锁；没有“某个进程崩在持锁状态”这种会卡住所有查询的故障。
2. 跨进程共用一个令牌桶（锁文件里存最后一次请求的时间）：大麦看到的总流量更准，但每个请求都要加锁、读写文件；开售那一刻 `watch` 每秒要确认一次能不能买（0002），这条路径上多一个可能卡住的锁，代价直接落在最要紧的几秒里。而且 theFlash 的正常用法是一个 `watch` 加偶尔一次界面查询，不是几十个进程并发。

## 决定

- 新增访问层 [`damai::access::Gate`](../../backend/src/damai/access.rs)，是 `Client` 唯一的出口。`Client::new` 创建它，每个请求（详情页、票档接口、读时钟的 HEAD）发出前都经过 `Gate::enter`。
- **熔断状态**用选项 1：`risk-stop.json`，内容是北京时间、触发的 URL、命中的页面标记、哪个命令（不含参数）和 pid。任何响应被识别为风控页时写入；写入失败时报告“风控已发生，但熔断没记下来，别的进程不会自动停”，而不是静默继续。
- **位置**：macOS 用 `~/Library/Application Support/theFlash/`（Apple 的 File System Programming Guide），Linux 用 `$XDG_STATE_HOME`，没设置时 `~/.local/state/theflash/`（XDG 规范里“跨重启保留的状态”）。只支持这两个平台，所以没有第三个分支。目录由 `HOME` 决定，测试在临时 HOME 下跑，天然不碰真实配置。
- **加锁**：同目录下一个 `risk-stop.lock`，用标准库的文件锁（`File::lock` / `lock_shared`，Rust 1.89 起稳定，不引入依赖）。读取取共享锁，写入和解除取排他锁，所以“读出来再删掉”是一个原子动作，解除命令报告的就是它真正清掉的那一条。写入本身是写临时文件再 `rename`，即使不加锁，读的人也不会看到半个文件。
- **频率上限**用选项 1：进程内所有调用方共用一个最小请求间隔 `MIN_REQUEST_GAP = 300ms`（沿用票档请求之间已经在用的 300 毫秒）。超出时在队列里等到自己的时隙，而不是直接发出。时钟可注入，测试用虚拟时钟而不是墙钟。跨进程不共用频率上限，理由见上；跨进程的安全网是熔断。
- **`THEFLASH_REQUEST_GAP_MS` 成为这一层的间隔**：[0009](0009-launchd-validation.md) 为无人值守验证加的这个环境变量，原来由 `Client` 自己在 get/head 前实现；现在它设置 `Gate` 的间隔，所以仍然覆盖每一个请求，范围和校验（0–86400000 毫秒，拒绝溢出）都不变。两条规则合起来是取较大值：显式设置只能把请求放得更慢，设成 0 或小于 300 的值也不会比 `MIN_REQUEST_GAP` 更快——共用的上限是底线，不该被一个环境变量绕开。不设置时行为就是上面的默认。
- **熔断不自动解除**，只有 `theflash risk resume --yes` 能解除。不带 `--yes` 的 `theflash risk resume` 只打印这次风控并提示“先确认 owner 已经看过”，退出码 2。`theflash risk` 显示状态，熔断生效时退出码 1。
- **状态文件损坏或目录不可写就停下并说明原因**：读不出来不等于没有熔断。`Gate` 在创建时就检查状态目录可用（建目录 + 打开锁文件），所以不是等到第一个请求才失败。
- **所有调用方都走这一层**：`theflash event`、`event-json`、`watch`，以及 #3 的界面。界面里 Node 进程内存的 `riskStopped` 删掉，改为把后端返回的 `risk-stopped` 当成“已停止”，并在页面上写出怎么解除。这一条取代 0004 里“服务的串行/风控锁只覆盖本服务”的部分。
- 风控识别和熔断在同一层，所以风控标记（`_____tmd_____`、`x5secdata`）只有一份，并且会记下是哪一个命中。

## 后果

- 一次查询比以前慢一点：以前详情页之后的第一个票档请求不等，现在也要等一个 300 毫秒的时隙。三场次的演出（4 个请求）从约 0.6 秒变成约 0.9 秒。换来的是“整条路径上每个请求都被同一个上限管住”。
- 读大麦时钟的 5 次 HEAD 不再自己 `sleep(250ms)`，由频率上限隔开 300 毫秒，总共约 1.2 秒。0002 要的“相位不同的几次采样”仍然成立，开售前 20 秒的重新同步也够用。
- 熔断生效时，所有命令都会失败并说同一句话，包括正在跑的 `watch`（它会提醒并退出）。这是故意的：owner 没看过之前，theFlash 不该继续碰大麦。
- 每个请求多一次本地文件读（取共享锁 + 读一个小文件）。在开售那一秒的路径上也有，量级是几十微秒，远小于一次大麦往返。
- 多了一个用户可见的命令（`theflash risk`），以后登录、购票前准备也从它这里拿“现在能不能请求大麦”。
- **#74 的修正（2026-10-14）**：这条决定没有变，但它当时的实现有四处漏掉了自己定下的规矩，都已在 #74 修好，细节见[访问层](../subsystems/damai-access.md)：
  - “每个请求都经过 `Gate`”对 reqwest 自动跟随的重定向不成立。现在自己一跳一跳跟随（最多 5 跳），每跳都排队和查熔断；`Location` 里的风控标记立刻记熔断并停下，不跟过去。
  - “进程内所有调用方共用一个上限”对两个默认 `Client` 不成立（各自 `Gate::for_user` 各有一份预算）。现在 `Gate::for_user` 一个进程只建一个。
  - 预约绝对时隙后只 sleep 一次，被延迟唤醒时会一次放完攒下的时隙。现在时隙在真正轮到时才占用。
  - “创建时就检查状态目录可用”只打开锁文件，旧锁文件在只读目录里照样能打开。现在真写一个临时文件验证。
- 出现下面的证据时应重新考虑：
  - 实际使用中出现“每个进程都在自己的上限内，但合起来触发了风控”——那就要实现跨进程的频率上限（选项 2），并解决持锁进程崩溃的问题。
  - 熔断文件所在的目录在某些用户的机器上不可写（例如被同步工具锁住），导致正常查询也被挡住。
  - 开售那一秒的实测显示每请求一次本地加锁影响了反应速度。
