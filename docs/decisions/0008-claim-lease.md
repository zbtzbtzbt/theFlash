# 0008. 认领是一条带过期时间的租约，写在 issue 的评论里

- 状态：采用
- 日期：2026-10-14
- 相关：#16、#20、#15（共用账号分不出 agent）

## 背景

一个 issue 同时只应该有一个 agent 在做，而我们没有调度中心：所有 agent 共用一个 GitHub 账号，彼此只能通过 issue 和 PR 上的文字交流。2026-10-14 夜里同时跑 6 条线时，三件事都发生了：

- 为了不让别的会话抢走给 Codex 的 #3，只能在 issue 正文里手写“负责：Codex（其他 agent 不要认领）”。正文是人写给人看的，脚本读不了，也没法在认领结束后自动失效。
- agent 的会话挂掉之后，它认领的 issue 一直显示有人在做。没有任何机制收回，只能等人来看。
- #4 和 #3 会改到同一批文件，可这件事只能靠读评论和代码才知道；#16 之前没有任何地方写着“这个认领会动哪些目录”。

约束：

- 不能引入常驻进程或外部服务。今晚的调度脚本是 3 分钟一次的轮询，agent 是一次性的进程，随时可能被断网或超时杀掉。
- 状态只能放在 GitHub 上。agent 跑在不同的 worktree、有时在云端，本地文件互相看不见。
- GitHub 的 `user.login` 分不出是哪个 agent（共用账号，见 [0007](0007-merge-gate.md) 和 #15），所以“谁在做”必须由内容自己声明。
- 这个仓库的套餐没有分支保护、没有审计日志，也没有 issue 的自定义字段。

## 考虑过的选项

- **只用标签**：`认领中` 加 `指派:codex`。标签能被 `gh issue list` 过滤，但一个标签存不下“改哪些模块”“什么时候过期”，而且标签的改动时间要翻 timeline 才看得到。
- **GitHub 的 assignee**：共用账号，所有 agent 都是同一个人，assignee 分不出是哪一条线，也不带过期时间。
- **仓库里的一个状态文件**（`claims.json`）：机器最好读，但每次认领和心跳都要提一个 commit，和正在进行的工作抢分支，rebase 冲突会盖掉别人的认领。认领这件事本身也不该进代码历史。
- **GitHub Projects 的自定义字段**：能存结构化字段，但要额外的 API 和权限，agent 读写都要新的依赖；issue 上看不到，评审和验收的人还得切一个界面。
- **issue 评论里一条固定格式的租约**（选中）：评论天然带 GitHub 自己的时间戳，所有 agent 都已经在写评论，人和脚本看的是同一份东西。

## 决定

认领 = `认领中` 标签 + 一条固定格式的认领评论。评论里写 agent、改动模块、分支和预计完成时间；[`backend/src/claim`](../../backend/src/claim/mod.rs) 读它，[`scripts/claims`](../../scripts/claims) 是它的命令行。细节见 [认领租约](../subsystems/claim-lease.md)。

四个取舍值得写下来：

1. **租约的时钟用 GitHub 的评论时间，不用正文里写的时间。** 正文里的 `开始时间` 是给人看的；判断用 `created_at`，手写的时间写错了也移不动过期时刻。
2. **心跳不要求专门的评论。** `## 心跳` 评论算，持有者签了 `Agent:` 的任何评论也算，推一次认领评论里写的分支也算——这正是 agent 本来就在做的事。别的 agent 的评论不算，否则一条审查意见就能让一个已经挂掉的会话看起来还活着。
3. **过期 120 分钟、心跳 30 分钟。** 和 #16 的要求一致。30 分钟是提醒，120 分钟才允许收回：今晚一个任务的时间盒是 3 小时，`make check` 加 CI 一轮十几分钟，30 分钟就收回会把还在跑检查的 agent 踢掉。
4. **冲突由命令拦，而不是靠读文档。** 认领时如果要改的模块和另一条进行中的租约重叠，命令直接拒绝；只有带上 `--overlap <怎么分工>` 才放行，并把这句分工写进认领评论。目录覆盖它下面的文件，所以 `backend/src/claim` 和 `backend/src/claim/lease.rs` 算重叠。
5. **同时认领用“最早的那条算数”+ 写后确认，不用锁。** GitHub 没有 compare-and-set：两个 agent 可以在同一秒里都读到“没人在做”、都发出认领评论，而 agent 跑在不同的 worktree、有时在不同的机器上，本地锁互相看不见。所以认领发出去之后再读一遍这个 issue：同一个窗口里**最早**的那条认领评论算数（同一秒用 GitHub 的评论 id 定序），两个 agent 读同一份评论会得出同一个结论；晚到的那个发一条 `## 让出认领` 说明自己作废、不加标签、以退出码 1 结束。代价是输的那个 agent 会在 issue 上留下一条作废的认领和一条让出评论——比两个 agent 同时开始做同一件事便宜得多。考虑过“只靠多读一次再判断”（读完还是会同时写，不解决问题）和“仓库里的锁文件”（又回到和代码抢分支的老问题）。
6. **“推分支算心跳”读的是推送时间（`repos/<仓库>/activity`），不是 commit 的提交时间。** `commits?sha=<分支>` 给的是 commit 自己的提交时间：离线写在 03:10、05:10 才推上去的 commit，看起来是两小时没动静，租约会被别人收回。GitHub 唯一说“什么时候推上来的”的地方是仓库活动。读活动需要仓库的 push 权限，读不到的时候**不回退**到 commit 时间，而是把这条租约标成“推送时间读不到”：证明不了它沉默，`reclaim` 和 `claim` 都拒绝，`list --json` 也不把它算成 `expired`。宁可一条租约暂时没人能接手，也不要用一个意思不对的时间把还在干活的 agent 踢掉。
7. **只认评论自己说的话，不认它引用的话。** agent 会在 issue 上贴自己跑过的命令和输出，而那些输出里就有完整的认领、心跳和收回评论（#31 的演示记录三样都有）。所以解析只看评论的顶层内容：围栏代码块（`` ``` ``、`~~~`）和引用行（`>`）里的 `## 认领`、`## 收回认领`、字段和 `Agent:` 签名都不算。否则一条进度汇报就能认领一个 issue，或者让两小时前被收回的租约复活。
8. **租约是评论，标签只是过滤器。** 命令先发评论再加标签，所以加标签失败会留下一条没有标签的租约。按标签过滤的看板（`issues?labels=认领中`）看不到它，所以每个只针对一个 issue 的命令（`claim`、`heartbeat`、`reclaim`）都额外读这个 issue 自己的评论，以它为准；心跳顺手把丢掉的标签补回去。全局 `list` 仍然只列带标签的 issue——要列出所有 issue 的评论就得把整个仓库翻一遍，太贵，而每一条认领路径都会在动手之前读到它。

和 [合并闸门](0007-merge-gate.md) 一样，这里不调用模型：所有判断都来自 GitHub 的响应和评论里的字段，所以调度脚本和 agent 对同一个 issue 得到的结论一样。它也和闸门一样不是服务端强制——手写一条评论、手动加标签仍然可以绕过，接受这一点的理由同 0007：目的是让正确的做法变成最省事的做法，并且让偏离留下痕迹。

## 后果

- 变容易：一条 `scripts/claims list` 就能看到今晚谁在做什么、哪条租约过期了；调度脚本用 `--json` 读同一份事实。会话挂掉之后，issue 不再永远显示有人在做。排期时能提前看到模块冲突，而不是在 rebase 时才发现。
- 变难：认领多了一步命令（`scripts/claims claim`）。认领评论的格式变成一个契约，改字段名要同时改 [`lease.rs`](../../backend/src/claim/lease.rs)、文档和已经发出去的评论——所以解析对写法宽容，判断只认那几个字段。
- 同时认领的结局是机械的，但不是没有痕迹：输的那个 agent 的认领评论留在 issue 上，后面跟一条让出评论。读 issue 的人要知道“最早的那条算数”才看得懂，所以让出评论里把这条规则写了出来。
- 读推送时间需要仓库的 push 权限。只读权限的 agent（或者以后换成 fine-grained token 的时候）会看到“推送时间读不到”，于是谁都收不回这条租约，只能等持有者自己发心跳或者在 issue 上说话。什么时候该重新考虑：如果这种情况常发生，就把“分支的 head 变了”本身做成心跳的证据（由调度脚本在观察到变化的那一刻记一条），而不是去问 GitHub 什么时候推的。
- 收回是机械的，但不是免费的：被收回的 agent 如果其实还活着（只是在跑一个很慢的检查而没说话），会看到自己的 issue 被别人接手。缓解办法是心跳便宜（任何签名的评论、任何一次 push 都算）和 120 分钟的窗口。真的被误收回时，重新认领一次就行，收回评论里写了怎么做。
- 什么时候该重新考虑：如果 agent 开始大量发无意义的心跳来保住租约，或者 120 分钟对某类任务（比如要等 10:18 开售的实测）太短，就把过期时间做成每条租约自己声明的字段，而不是全局常量。如果以后仓库升级到带 Projects 字段或审计日志的套餐，可以把看板换成结构化字段，但评论仍然是人读的那一份。
