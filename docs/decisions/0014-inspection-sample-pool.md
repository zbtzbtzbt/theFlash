# 0014. 巡检样本：不爬列表，靠候选池自愈，补不上就报警

- 状态：采用
- 日期：2026-10-14
- 相关：#39、#10（巡检）、[0011](0011-damai-revision-inspection.md)、[0001](0001-damai-event-data-source.md)

## 背景

改版巡检（[0011](0011-damai-revision-inspection.md)）每次查五类演出：已开售、未开售、已售罄、日历选日期、电脑版不卖。样本会过期——未开售的演出到点就开售了，开售的演出会售罄、会下架——所以 #10 要求“样本能自动换新”。

#10 实现时从首页取候选，2026-10-14 04:01 实测发现首页匿名 HTML 里一个演出链接都没有（卡片是 JS 渲染的），于是 #39 要求另找一个匿名可用的列表来源。约束没变：不登录、只读、不做批量抽样；所有 agent 共用 owner 家里一个出口 IP，#2 的盯票常常同时在跑；搜索接口第一次匿名请求就返回滑块页（[0001](0001-damai-event-data-source.md)），不能用。

2026-10-14 04:17–04:21 持 `damai-lock` 实测了 #39 列出的候选来源，8 个请求，相邻 ≥3 秒，没有滑块、验证码或限流（证据：[docs/validation/issue-39.md](../validation/issue-39.md)）：

| 来源 | 结果 |
| --- | --- |
| `www.damai.cn/`（PC 首页） | 200，16 KB，没有一个 `detail.damai.cn` 链接；唯一的列表入口是 `search.damai.cn` |
| `m.damai.cn/`（移动版首页） | 200，但只有 2.6 KB 的 SPA 壳子，连一条数据都没有，内容全靠 `g.alicdn.com` 的 JS 去 mtop 拉 |
| `t.damai.cn/yep/page/m/…`（首页上那四个活动页） | 200，20 KB，是营销页（其中一个是“大麦商家入驻流程”），没有演出 ID，数据同样来自 `mtop.damai.cn` |
| `www.damai.cn/robots.txt`、`www.damai.cn/projectlist.do` | 两次都是 20 秒超时没有任何响应（首页在同一分钟内正常，所以不是本机网络或限流） |
| `detail.damai.cn/robots.txt` | 302 到淘宝的错误页 |
| `m.damai.cn/robots.txt` | 200：`User-agent: *` / `Allow: /.well-known` / `Disallow: /` |

两条结论：**大麦今天没有任何匿名可用、服务端渲染的演出列表**，所有列表都是 JS + 要签名的 mtop 接口（[0001](0001-damai-event-data-source.md) 说过 mtop 要 `_m_h5_tk`）；而且大麦唯一对外发布的抓取策略写的是“整站不要抓”。

## 考虑过的选项

1. **逆向首页/移动版调的 mtop 列表接口**。能拿到全站演出。代价：要自己算 `_m_h5_tk` 签名，这是绕过大麦的访问控制，触碰 owner 定下的“不绕过任何风控”（#6）；而且接口一改就坏。
2. **爬 `m.damai.cn` 或分类页**。代价：这些页面本身就没有数据（实测 2.6 KB 的壳子），而且 `m.damai.cn/robots.txt` 明确 `Disallow: /`。为了换样本去做一件大麦明说不要做的事，不值得。
3. **用浏览器（computer use）渲染一次首页，把 itemId 存进样本文件**。能拿到真实候选。代价：巡检是定时无人值守任务（#9、#17），再挂一个浏览器就不是无人值守了，而且每次都要起 Chrome。
4. **把样本写死在仓库里，过期了人工换**（#10 现在降级后的行为）。代价：没有任何提醒，样本一过期巡检就安静地少查一类，CI 和退出码都看不出来——这正是巡检最怕的“绿着瞎了”。
5. **仓库里维护候选池 + 把读到的演出按它现在的状态重新归档 + 补不上就当成发现报出来**（选中）。不碰任何列表，不多发一个请求，自愈能覆盖演出自己会走的状态变化；覆盖不了的那部分不假装覆盖，而是报警。

## 决定

采用方案 5。巡检不再把“找新演出”当成自己的能力，而是把“样本不够用”当成一个必须被人看见的发现。

- **一类可以有多个样本**。样本文件里每一类保留最多 `KEEP_PER_CATEGORY`（3）个：第一个是下一次要读的，后面是备用。读样本还是一类一个请求，备用样本不花请求。
- **按现在的状态重新归档**。每次读到的页面，按它**现在**显示的状态归档，而不是按它被保存成哪一类。演出自己会沿着“未开售 → 已开售 → 已售罄”走，所以已开售和已售罄这两类靠这一条就能自己补上，不需要任何列表。
- **候选顺序**：这台机器存下来的备用样本 → 仓库里的候选池（`inspect::samples::POOL`，`testdata/damai/` 录自哪一场就是哪一场打头）→ 首页。首页排最后：它今天给不出东西，但只要 1 个请求，大麦哪天把链接放回来它就自己恢复了（`the_recorded_home_page_carries_no_detail_link` 盯着这一天）。
- **候选池由人/agent 手工加**。理由就是上面实测的两条：没有能用的列表，大麦也说了不要抓。加一场演出就是在 `samples.rs` 的 `POOL` 里加一个 itemId。
- **补不上就是发现**。某一类的候选全部试完还覆盖不了，报“样本缺口”、指出要改哪个文件、退出码 1、`--open-issue` 时开 issue。这和“`--max-events` 预算没轮到这一类”分开：后者下一次预算够了就覆盖了，不是发现。
- **提前报过期**。大麦会提前告诉你未开售的演出什么时候开售（`dataDefault.sellStartTime`）。这一类的样本在开售前 3 天（`NOTICE_BEFORE_EXPIRY_MS`，约等于三次每日巡检）开始报“样本快过期”，也是发现。找一场新演出要人去找，所以提醒必须在这一类真的没样本之前发出来。其他四类大麦不预告（没有页面会说自己哪天售罄），所以只有未开售这一类有提前量。

怎么用、请求总数、样本文件长什么样，写在 [subsystems/damai-inspect.md](../subsystems/damai-inspect.md)。

## 后果

- 巡检不会再安静地少查一类：少查就是退出码 1 加一条 issue 评论，说明要把哪个 itemId 写进哪个文件。
- 已开售和已售罄两类基本不用管了，它们顺着演出自己的生命周期流动；未开售和日历选日期两类迟早要人补，但有 3 天提前量。
- 巡检的请求数不变（样本都有效时 9 个），首页只有在候选池用完时才请求一次。
- 候选池在仓库里，所以“今天哪几场演出可以当样本”会被 review 看到，也会随代码一起发版。代价是它会和真实世界慢慢脱节：池子里的 itemId 不保证现在还是那个状态，巡检只是按顺序试。
- 出现以下证据时应重新考虑：大麦恢复服务端渲染的演出链接（首页那条测试会红）；大麦发布一个明确允许抓取的列表（例如 `www.damai.cn/robots.txt` 真的能访问并且允许某些路径）；候选池需要补的频率高到每周都要人动手，说明该为巡检单独准备一个长期有效的样本来源（例如 owner 指定几场长期在售的演出）。
