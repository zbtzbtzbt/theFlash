# 0004. 浏览器界面通过本机 TypeScript 服务复用 Rust 查询

- 状态：已被 [0013](0013-standalone-event-ui.md) 取代（风控熔断部分已被 [0005](0005-damai-access-gate.md) 取代）
- 日期：2026-10-14
- 相关：#3、#2、#4、#5

## 背景

#3 要求一条命令启动、只允许本机访问的演出查询界面，且信息与 `theflash event` 一致。现有 Rust 查询已经用真实页面核对了状态映射、场次顺序和失败行为。界面不登录、不下单，也不需要持久化状态。

## 考虑过的选项

1. Rust HTTP 框架服务并嵌入前端：未来适合单二进制发布，但现在需引入 HTTP 框架及前端产物嵌入流程，容易让单独构建 CLI 依赖 Node。
2. Node 内置 HTTP 服务 + Rust 子进程：不增加产品运行库，共用已安装的 Node/TypeScript；CLI 仍可独立构建。代价是启动界面需要 Node 和 Rust 二者，查询多一次进程启动。
3. 前端直接解析大麦：跨域限制、重复状态映射和风控逻辑，不能可靠保持 CLI 一致。

## 决定

采用方案 2。`make serve` 安装前端锁定依赖、构建前后端，再启动本地服务。服务绑定 `127.0.0.1` 的操作系统分配端口并打印 URL。前端使用 TypeScript 和原生 DOM，先用 `tsc` 编译，再以同源静态文件提供；不需要 UI 框架和打包器。DOM 测试使用 happy-dom + 已有 Vitest，仅作为开发依赖。

增加内部 `event-json` 命令，复用 `event` 的输入解析与 `Client::event`；JSON 的显示文字和北京时间格式直接共用 CLI renderer，避免前端自己推导状态。ID 用字符串传输，避免 JavaScript 数字精度问题。普通 `event` 的文本、退出码及错误行为不变。

本地服务校验 Host 和 POST Origin，不提供 CORS，固定静态文件白名单，不将输入传给 shell。整个服务一次只允许一个查询；断开页面连接会取消 Rust 子进程。风控错误锁住本次服务的后续查询，跨标签页也不能重试；只有 owner 决定下一步之后才应重启服务。界面和服务都不自动重试。

## 与后续工作的边界

已读 #3 中 Claude 的架构意见。当前决定提供源码 checkout 中的一条命令入口，前端构建工具链本就使用 Node，CLI 本就需要 Rust；这一轮不声称单文件 GUI 发布包已经可用。#5 的直接运行产物是新的发布需求，在它发版之前必须重新评估嵌入前端的 Rust HTTP 服务或完整运行时打包，确定产物之后才发 tag。

#2 的持续盯票已经合并，是实际存在的长期任务；它不应反复启动短命子进程。本次 `loadEvent` 只负责一次查询；接入长期任务和推送状态时重评 HTTP/SSE 的所有权边界，不沿用一次查询接口去轮询子进程。服务的串行/风控锁只覆盖本服务，不与其他 CLI 进程共享；全进程请求频率和风控停止由已打开的 #4 跟进。这些边界是本轮选择的代价，并未声称已解决。

## 后果

- 保持现有 Rust 数据源与 CLI 的事实来源；只增加展示契约和本地入口。
- 发布单二进制、长期运行任务或大量并发查询成为实际需求时，重新评估 Rust HTTP 服务，而不是现在提前实现。
- UI 测试启动本地服务器并回放 #1 保存的真实响应，不访问真实大麦；服务和子进程在测试结束时清理。
