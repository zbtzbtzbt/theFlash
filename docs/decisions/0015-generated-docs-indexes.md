# 0015. docs 的两张索引表由脚本从目录生成，并发 PR 不再碰同一行

- 状态：采用
- 日期：2026-10-14
- 相关：#45、#20、PR #24、PR #32

## 背景

`docs/decisions/README.md` 和 `docs/subsystems/README.md` 各有一张索引表。以前每条新决定、每份新子系统参考都往表的**末尾追加一行**，于是两个并行的 PR 改的是同一个位置，git 必然冲突。

2026-10-13 夜里五六条线并行开发，这两张表把 PR 打回了 4 次（PR #24 两次、PR #32 两次），没有一次和代码有关。代价不是解冲突那几秒：按本项目的规则，冲突的 PR 要退回 `要修改`，实现者 rebase、重跑 `make check`、等双平台 CI，再重新交审查、审查者重新验证，一次来回半小时起；rebase 完成前 main 可能又前进了，于是再来一轮。PR #32 就是这么卡住的——审查已经通过，拿到合并锁时 main 前进，两张表同时冲突，只能退回。

约束：索引要留在 README 里（GitHub 上点进目录第一眼就能看到有哪些记录、各是什么状态），不能依赖 CI 以外的人工约定，而且规则要能机械判断——这是 [code-standards](../code-standards.md#ci-必须有的) 已有的要求。

## 考虑过的选项

- **表由脚本从目录生成，`scripts/check.sh` 守护。** PR 只新增自己那个 Markdown 文件，索引由 `make docs-index` 重新写出来。冲突从“两个人编同一行文案”变成“两个人跑同一个确定性命令”，而且顺手能发现“写了记录但忘了进索引”“标题改了索引没改”这类漂移。代价：多一个脚本和一条检查。
- **删掉表，只留一句“记录在本目录下，编号递增”。** 最省事，冲突也没了，但点进目录只看得到文件名，看不到状态（哪条已被取代），索引的价值基本没了。
- **只配 `.gitattributes` 的 union 合并。** 两边的行都保留，不产生冲突；但 union 不保证顺序（0015 可能排在 0009 前面），也不会发现漏登记，表头被两边同时改时还会留下重复行。单独用不够。
- **什么都不改，约定由审查者解冲突。** 今晚的规则不允许（审查者不能变成实现者），而且不消除 rebase + 重跑 CI 的成本。

## 决定

做第一个，并把 union 合并当兜底，两者一起用：

- [`scripts/docs_index.py`](../../scripts/docs_index.py)（标准库，和 [0009](0009-launchd-validation.md) 的 `validation.py` 一样）从 `docs/decisions/NNNN-*.md` 和 `docs/subsystems/*.md` 生成两张表，写回各自 README 里 `<!-- docs-index:begin -->`/`<!-- docs-index:end -->` 之间，标记以外的正文一字不动。
- 事实来源是文件本身：决定记录的标题取一级标题、状态取 `- 状态：` 那一行；子系统参考的标题取一级标题、索引用的一句话取一级标题下面那行 `> …`。表里不再有只存在于 README 的文案（原来 0004 在表里和在记录里就是两个不同的标题）。
- `make docs-index` 生成，`scripts/check.sh` 里的 `python3 scripts/docs_index.py --check` 守护：对不上就失败，并说明少了哪行、多了哪行还是顺序不对，以及跑哪条命令修好。
- [`.gitattributes`](../../.gitattributes) 给这两个 README 配 `merge=union`：并行 PR 各加一行时，rebase 和合并不再停下，两行都留着；万一顺序不对，上面那条检查会拦住，跑一次生成命令即可。union 只对这两个文件开，因为它们的改动几乎全在生成区里。

## 后果

- 并行 PR 不再因为索引表互相冲突：它们只新增自己那个文件，生成出来的行各不相同，union 合并不会停。
- 漏登记、标题漂移、删了文件没删索引，现在是 `make check` 里的一条红，而不是靠人读 diff 发现。
- 新增一份子系统参考时必须写 `> 一句话`，否则检查失败并告诉作者写在哪。
- union 合并对标记以外的正文不安全：两个 PR 同时改这两个 README 的前言，会把两边的句子都留下而不冲突。这两份前言很稳定，而且生成区由检查守着；如果以后出现前言被 union 弄乱的实例，就撤掉 `.gitattributes` 这一条，只留生成和检查。
- 这个改动自己会和所有“手改过索引表”的在途 PR 冲突最后一次：它们 rebase 时丢掉自己对两个 README 的改动，保留自己新增的那个文件，跑 `make docs-index` 即可。
- 以后再出现“并行 PR 必然冲突”的共享文件（例如将来的变更日志），照这个模式办：事实留在各自的文件里，汇总由脚本生成。
